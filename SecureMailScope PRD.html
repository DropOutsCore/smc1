SecureMailScope

Product Requirements Document

AI-Assisted Cryptographic Security Posture Assessment for Secure Email Communications

1. Overview

Email transport security (SMTP, IMAP, POP3 over TLS/STARTTLS) is frequently misconfigured — obsolete TLS versions, weak ciphers, broken STARTTLS, expired or misissued certificates — yet most network analysis tools only decode packets; they don't score risk or tell an analyst what to fix first.

SecureMailScope is a passive network forensic framework that ingests PCAP captures of email traffic, reconstructs the full session lifecycle (TCP → protocol handshake → STARTTLS → TLS negotiation → certificate exchange), and uses AI/ML to classify cryptographic risk, flag anomalous TLS behavior, and generate prioritized, exportable security reports.

Primary users: SOC analysts, Digital Forensics & Incident Response (DFIR) teams, enterprise security/email administrators, compliance auditors.

2. Goals

# Goal
G1 Passively analyze SMTP/IMAP/POP3 PCAPs with zero active interaction with the network
G2 Reconstruct complete sessions and TLS handshakes with high fidelity
G3 Automatically detect cryptographic weaknesses against current best-practice baselines (NIST/IETF)
G4 Apply AI/ML to score risk, detect anomalies, and rank findings by severity
G5 Produce forensic-grade, exportable reports (JSON/PDF/HTML) and a live dashboard

Non-goals: decrypting TLS payloads without keys, active MITM testing, real-time traffic blocking, or acting as a mail server/proxy.

3. Personas

  • SOC Analyst — needs a fast, prioritized view of which mail servers/sessions are cryptographically weak, right now.
  • DFIR Investigator — needs a reproducible, chain-of-custody-friendly report tying findings to specific packets/streams for post-incident review.
  • Enterprise Email Admin — needs plain-language remediation guidance (e.g., "disable TLS 1.0 on mail.corp.com") without needing to read raw handshake bytes.

4. Scope

In scope

  • Offline/batch analysis of .pcap/.pcapng files
  • SMTP, IMAP, POP3 (including implicit-TLS variants: SMTPS 465, IMAPS 993, POP3S 995)
  • STARTTLS detection and downgrade-attempt detection
  • TLS 1.0–1.3 handshake parsing, cipher suite / key exchange extraction
  • X.509 certificate parsing, chain, and expiry validation
  • AI/ML risk scoring, anomaly detection, and mitigation recommendations
  • JSON/PDF/HTML report export + interactive dashboard

Out of scope (v1)

  • Decrypting application-layer email content
  • Live/inline packet capture or blocking
  • Non-email protocols (HTTP, FTP, etc.)
  • Automated remediation (the tool recommends; it does not act)

5. Functional Requirements

5.1 Protocol & Session Reconstruction

  • FR-1 Auto-identify SMTP/IMAP/POP3 traffic by port and payload signature (not port alone, to catch non-standard ports).
  • FR-2 Reassemble full TCP streams per session, handling retransmission, out-of-order segments, and fragmentation.
  • FR-3 Detect STARTTLS command/response and mark the exact transition point from plaintext to encrypted stream.
  • FR-4 Flag STARTTLS stripping/downgrade patterns (e.g., plaintext continues after a STARTTLS command was observed).

5.2 TLS Handshake Analysis

  • FR-5 Parse ClientHello/ServerHello, extract negotiated TLS version, cipher suite, extensions (SNI, ALPN, supported groups).
  • FR-6 Identify key exchange mechanism (RSA static, ECDHE, DHE) and derive Perfect Forward Secrecy (PFS) status.
  • FR-7 Detect deprecated/insecure protocol versions (SSLv2/3, TLS 1.0/1.1) and weak/export-grade or NULL/RC4/3DES cipher suites.
  • FR-8 Detect anomalous or malformed handshakes (unexpected renegotiation, incomplete handshake, non-standard extensions).

5.3 Certificate Analysis

  • FR-9 Extract X.509 certificates from the handshake (Certificate message) and reconstruct the presented chain.
  • FR-10 Validate chain of trust, and separately report (without failing analysis on) self-signed or untrusted roots.
  • FR-11 Check validity window (not-yet-valid / expired) and expiry-proximity warnings (e.g., <30 days).
  • FR-12 Extract public key algorithm and key length (flag RSA <2048, ECC <224) and signature algorithm (flag MD5/SHA-1 signed certs).
  • FR-13 Check hostname/SAN match against observed SNI/destination.

5.4 Cryptographic Weakness Detection

  • FR-14 Rule engine mapping findings (5.1–5.3) to a curated weakness catalog (deprecated TLS, weak ciphers, weak keys, no-PFS, cert issues), each tagged with CWE/CVE or standards reference (NIST SP 800-52, IETF RFC 8996) where applicable.
  • FR-15 Deduplicate and correlate repeated findings across sessions to the same host/service.

5.5 AI/ML Risk Intelligence

  • FR-16 Feature extraction pipeline converting each session's protocol/TLS/certificate attributes into a structured feature vector.
  • FR-17 Supervised risk classification model producing a per-session and per-host cryptographic risk score (e.g., Critical/High/Medium/Low) with contributing-factor explainability.
  • FR-18 Unsupervised anomaly detection model (e.g., isolation forest / autoencoder) to flag TLS sessions that deviate from the baseline of "normal" traffic for that environment, catching novel/unlabeled misconfigurations or attack patterns.
  • FR-19 Threat prioritization: rank findings by (severity × exposure × exploitability) rather than raw count.
  • FR-20 Auto-generated, human-readable mitigation recommendations per finding (templated, informed by the finding type).

5.6 Reporting & Visualization

  • FR-21 Export full findings as structured JSON (machine-readable, for SIEM/SOAR ingestion).
  • FR-22 Export a formatted PDF forensic report (executive summary + technical appendix + evidence references).
  • FR-23 Export an HTML report viewable offline.
  • FR-24 Interactive dashboard: posture overview, per-host drill-down, findings table with filters/sort, session timeline view.

6. Non-Functional Requirements

Category Requirement
Performance Process a 1 GB PCAP with mixed email traffic in a bounded, predictable time; stream-process rather than load entire capture in memory
Scalability Support batch analysis of multiple PCAPs / large enterprise captures
Forensic integrity Read-only analysis; never modify source PCAP; every report finding traceable to packet/stream offsets for evidentiary use
Security Sandbox untrusted PCAP parsing (malformed captures are a common attack vector); no external network calls during analysis
Usability Findings must be understandable by an admin without deep TLS expertise
Extensibility Weakness rule catalog and ML feature set should be updatable without code changes (config/rules-driven)
Compliance Align detection baselines with NIST SP 800-52 Rev.2 and current IETF deprecation RFCs

8. AI/ML Component Detail

  • Inputs (feature vector per session): protocol type, TLS version, cipher suite (+ strength category), key exchange type, PFS flag, cert key length/algorithm, cert validity window, chain trust status, handshake anomalies, STARTTLS timing/behavior.
  • Risk classification model: multi-class or ordinal classifier → {Critical, High, Medium, Low, Informational}, trained on labeled configurations built from known-good/known-weak baselines; must expose feature importances so a finding can say why it's rated Critical.
  • Anomaly detection model: unsupervised, trained per-environment on the observed traffic baseline, to catch misconfigurations or behaviors the rule engine doesn't have a rule for yet (novel downgrade techniques, unusual cert reuse, timing anomalies).
  • Recommendation generation: rule-templated (not free-form generative) to guarantee accuracy and auditability of security guidance — each recommendation is deterministically tied to a finding ID.

12. Risks & Assumptions

  • Assumption: Analysis is passive/offline on captured PCAPs — no assumption of live network access or decryption keys.
  • Risk: Malformed/adversarial PCAPs could crash parsers → mitigate with defensive parsing and sandboxing.
  • Risk: ML risk model needs representative labeled training data — mitigate by combining rule-engine baselines (rules give guaranteed-correct labels) with supervised learning on top.
  • Risk: TLS 1.3's encrypted handshake fields (post-ServerHello) limit passive visibility into some parameters — v1 scope should rely on what's visible in ClientHello/ServerHello/Certificate messages and document this limitation explicitly in the report.
